# Localisation (i18n)

> **Added:** 2026-10-23 · **Gap:** [G-09](gaps.md#g-09-localization) · **Crate:** `soundcraft-i18n`
> (`crates/i18n`, layer 0, standalone)

This is the localisation **runtime and catalog** for Pa Tools. It is deliberately a crate on its
own: the migration of the UI's string literals (`crates/ui-egui`) onto it is a **separate lane** and
has not happened yet — nothing in `ui-egui`, `engine` or `mix` uses this crate so far.

## What it does

- Looks English source text up in a per-locale catalog, **falling back to English** when there is no
  translation. A missing translation is never an error and nothing in the crate panics (errors are
  values; a malformed catalog row is skipped and reported).
- **Plurals** by CLDR rules (`intl_pluralrules`): one form for Japanese, two for French, three for
  Russian, six for Arabic, …
- A **language picker** (`languages()`, each language's own name via `name()`), the **system
  locale** (`system_lang()`), and **right-to-left** detection (`rtl()`; laying text out in display
  order is the UI's job).
- A **debug-only pseudo locale** that rewrites every looked-up string as `[!! Ŝèţţîñĝš !!]`
  (accented letters, bracketed, line by line), so any text drawn without the brackets is text that
  bypassed translation.

## Catalog

`crates/i18n/catalog/<locale>/common.tsv`, one tab-separated row per string:

```
context <TAB> English source text <TAB> translation
```

- **Source text is the key** — English is never translated, so there is no English catalog. The
  canonical list of keys Pa Tools translates is `crates/i18n/catalog/KEYS.txt`.
- **Context** is usually empty. `@id` (the source is a command id; the translation is its label) and
  `@plural` (`one|other` English forms; the translation lists this locale's forms, `|`-separated)
  are the reserved contexts; any other word (`menu`, `preview`) tells two meanings of the same
  English apart, and the app falls back to the plain row.
- `{name}` **placeholders** must appear in both columns; a trailing `…` in one needs one in the
  other; escapes are `\n \t \\`. An empty translation is an error — leave the row out and the string
  shows in English.
- Each `common.tsv` names its own language in a `@id language.name` row, for the picker.

The catalogs are compiled into the crate with `include_str!` (`src/builtin.rs`); there is no build
script and no environment variable. (The donor runtime left embedding to the app; Pa Tools ships one
catalog, so it embeds its own.)

### Fallback order

For `pt-br`, a lookup tries `pt-br` → `pt` → the English source. Only a **region** falls back
(`pt-br` → `pt`, `zh-hant-hk` → `zh-hant`); a **script** never does (`sr-latn` never falls back to
Cyrillic `sr`). Within a locale, an app row overrides a shared one, and `tc`/`tid` try their
context/`@id` row before the plain row.

## API

Two ways to use it. The UI lane will use the global one.

```rust
use soundcraft_i18n as i18n;

// Explicit: build a runtime, pass a Lang to each lookup.
let (i, problems) = i18n::pa_tools();
problems.iter().for_each(|p| log::warn!("translation catalog: {p}"));
let fr = i.from_code("fr").unwrap_or(i18n::Lang::EN);
assert_eq!(i.t(fr, "Save"), "Enregistrer");

// Global: one process-wide runtime, a current language, and the macros.
i18n::use_system_lang();          // or i18n::set_lang_code("fr")
i18n::tr!("Save");                // plain, current language
i18n::trc!("menu", "Open");       // with a context
i18n::trid!("file.save", "Save"); // a command label by id
i18n::trn!(n, "{n} item", "{n} items"); // a count
```

`global()` builds the process-wide runtime once from the embedded catalog; `set_lang`,
`set_lang_code` and `use_system_lang` change the current language and take effect on the **next
lookup** (this is how Pa Tools switches language while running). `problems()` returns any catalog
problems for the app to log once at start-up.

## How a later lane migrates the UI's strings

1. **Pick the language once, at start-up.** In `apps/soundcraft` read the user's language setting
   (`"auto"` → `i18n::use_system_lang()`, otherwise `i18n::set_lang_code(code)`) and log
   `i18n::problems()`.
2. **Wrap literals.** Replace a user-visible literal `ui.button("Save")` with
   `ui.button(i18n::tr!("Save"))`; a menu or two-meaning string with `trc!`; a command label with
   `trid!` keyed on the command id; a counted string with `trn!`. Product strings that come from
   `crates/brand` stay as they are — they are names, not translated text.
3. **Grow the catalog.** Every newly wrapped English string is a key: add it to `KEYS.txt` and, when
   a translation exists, a row to each `common.tsv`. Strings without a translation simply show in
   English. Keep reusing the donor craft-i18n catalog for exact English-source matches (see
   "Regenerating" below); send the rest for human translation.
4. **Find what you missed.** In a debug build, choose the `pseudo` locale: everything that still
   reads as plain ASCII (no `[!! … !!]`) is a string that bypassed `tr!`. `I18n::looked_up()` lists
   what was looked up, for an audit against `KEYS.txt`.
5. **Add the language picker.** List `i18n::global().languages()` with `name(lang)`; on change,
   `i18n::set_lang(lang)` and request a repaint.
6. **Right to left and fonts.** For an RTL language (`rtl(lang)` true, e.g. Arabic) the UI must lay
   widgets and text out in display order — egui does not do bidi reordering for you. For glyphs
   outside the bundled Latin fonts, register a fallback face (see Fonts).

## Fonts (not bundled in this lane)

Pa Tools bundles no font files yet (`ATTRIBUTION.md`, Fonts). egui 0.36 **does** shape complex
scripts — epaint shapes with `harfrust` (a Rust HarfBuzz port) — so the shaping engine is not the
blocker; the missing piece is **glyph coverage**: egui's built-in fonts (Ubuntu-Light, Hack, Noto
Emoji) cover Latin, Cyrillic and Greek but not CJK, Arabic, Thai or many others. A later lane that
turns an offered non-Latin locale on must register a fallback face for it.

The [storytold/craft-fonts](https://github.com/storytold/craft-fonts) repository (code MIT OR
Apache-2.0; each font **OFL-1.1**) has openly licensed faces. For Pa Tools' ten offered locales:

| Offered locale | Script | Covered by | craft-fonts face (OFL-1.1) |
|---|---|---|---|
| de, es, fr, it, pt-br | Latin | egui built-in (Ubuntu-Light) | — |
| ru | Cyrillic | egui built-in (Ubuntu-Light) | — |
| ja | Japanese (kana + kanji) | — | **BIZ UDPGothic** (UI sans); Shippori Mincho / BIZ UDMincho for document serif |
| zh-hans | Simplified Chinese (Han) | — | **Noto Sans CJK SC** |
| zh-hant | Traditional Chinese (Han) | — | **not in craft-fonts** — needs Noto Sans CJK **TC** (OFL-1.1), added there or bundled directly |
| ar | Arabic (RTL) | — | **Noto Sans Arabic** |

craft-fonts also carries **Noto Sans Thai** and **Noto Sans Georgian** (both OFL-1.1) for locales Pa
Tools does not offer yet. When a font lane lands, each bundled face gets a `fonts/manifest.txt`-style
row and an `ATTRIBUTION.md` row, per `AGENTS.md`. Note `zh-hant` has no face in craft-fonts today, so
offering Traditional Chinese needs a Traditional face.

### Regenerating the catalog from a newer donor

The catalog is checked-in data, reproducible from a craft-i18n checkout at the pinned commit:

1. `git clone https://github.com/storytold/craft-i18n && git -C craft-i18n checkout <commit>`.
2. For each key in `KEYS.txt`, take the row with that exact English source from
   `craft-i18n/locales/<locale>/common.tsv` (plain context), plus each locale's `@id language.name`
   and any reused `@plural` rows.
3. Write `crates/i18n/catalog/<locale>/common.tsv` with the Pa Tools header, and update the commit
   in this file and `ATTRIBUTION.md`.

Then `cargo test -p soundcraft-i18n` (the consistency tests check every row parses, every plain
source is a known key, no value is empty, and every locale names itself).
